# Events & Messaging

Required delivery model: transactional outbox + at-least-once delivery. Durable acceptance is available; producer migration and consumption remain pending in the [implementation plan](../transactional-outbox-implementation-plan.md). Missing guarantees are gaps, never exemptions. Run API and consumers in the same NestJS process per application instance; no separate worker deployment.

- `event-bus` owns event contracts/routing; `job-queue` owns pg-boss, atomic job insertion, pool/lifecycle, provisioning and queue policies. Depend on `IJobQueuePort`; queue infrastructure never imports event contracts or modules.
- Require successful `db:delivery:migrate` completion before rollout ([deployment](../docs/transactional-outbox-phase-3.md)); runtime never migrates or reindexes. All schema clients share one `DELIVERY_POOL_SIZE` pool.
- Define complete context-owned catalogs with `defineDeliveryRoutes`; duplicate targets per event fail. `EventBusModule.register(routes)` and `src/script/job-queue-migration.ts` use the same catalogs; derive queues only from their targets.
- `IEventPublisherPort.publish` atomically enqueues all targets through the ALS primary transaction, opening one if absent. Completion awaits inserts, not consumers; durability requires commit. Missing routes fail; omit consumerless events without removing mutation/audit.
- Keep `emitAsync` immediate/non-durable until producer migration; delivery may precede commit or survive rollback. Only `event-bus` uses `EventEmitter2`; durable consumers dispatch only committed events.
- `DurableEvent` carries only `{ eventId, eventType, aggregateId }`; use versioned enum names. Generate `eventId` once before persistence and preserve it across retries/replays. Consumers re-read authoritative state through owned ports/facades, never infer historical state ([Audit](observability.md#audit)).
- `DeliveryRecord` separates `event` from optional `telemetry` (`traceId`, `traceparent`); population and consumer tracing remain planned in Phase 5a.
- Consumers tolerate duplicate, concurrent, and out-of-order delivery. Prefer idempotent reconciliation; otherwise deduplicate by `(consumer, eventId)` atomically with DB effects. External effects require provider idempotency or explicit duplicate tolerance; use email-provider idempotency when available, otherwise duplicate emails are acceptable.
- In-process subscriptions use `OnAppEvent` in `application/event/`; network ingress uses `presentation/listener/`. Thin listeners dispatch commands owning reads, mutations, and idempotency; pass `eventId` when needed. Cache eviction may call its port directly.
- Await required listener work; propagate failures to the relay. Complete delivery only after all required consumers succeed; preserve failed work for retry/recovery. Relay claims must recover after worker failure and support multiple instances.
- Persist retry state; provide backoff, stalled/failed-delivery monitoring, and replay. Clean delivery/dedup records only under a retention policy covering supported retries/replays ([Observability](observability.md#observability)).
- Same-module cache eviction combines awaited best-effort pipeline eviction with retryable in-process event eviction, sharing `<module>-cache-key.util.ts`. Event-path failures must remain visible ([Adapters](data-and-state.md#adapters)); idempotent deletion needs no inbox and does not guarantee race-free freshness.
- Keep delivery infrastructure behind ports; use in-process dispatch in the monolith and brokers for extracted consumers without changing application semantics.
