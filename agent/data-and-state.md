# Data & State

## Domain State

- Aggregates own business rules: mutation eligibility, transitions, no-ops, and state-dependent delivery/cleanup decisions. Handlers coordinate I/O, persistence, transactions, and audit; never duplicate those rules.
- Aggregate prechecks/decision queries never mutate state or enqueue jobs. They may gate external I/O but never replace mutator validation; assertion methods reject by throwing.
- Handlers pass external facts and password-verification results into mutators; password hashing stays behind application ports. Keep database constraints for concurrency safety.
- Keep only universal aggregate mechanics in `AggregateRoot`; put optional shared invariants in specialized bases that aggregates explicitly extend. Admin/User use the existing `PrincipalAggregateRoot` hierarchy, which inherits durable-job accumulation from `AggregateRoot`.
- Valid idempotent requests for the current state are no-ops without jobs; invalid transitions fail.
- Keep Admin/User aggregate structure aligned: state; construction/snapshot; workflow methods in lifecycle order; corresponding protected/private helpers; getters in state-field order.
- `SoftDeletableAggregateRoot` mutations call `assertNotDeleted`, except repeat-safe deletion. Writers load only non-deleted aggregates; reaching a mutator with deleted state is a `SystemException`.

## Persistence & Transactions

- Each bounded context owns its tables/Drizzle definitions in its same-named PostgreSQL schema; no central table registry. Core owns `audit.audit` and `idempotency.idempotency`; `audit-trail` reads the exported audit table through the replica path. Keep `drizzle.config.ts` discovery and `schemaFilter` aligned with application-owned schemas.
- Do not use cross-module database JOINs, foreign keys, or shared synchronous transactions. Cross-context references are soft UUIDs; reads use facades and mutations use durable jobs ([Module Isolation](architecture.md#module-isolation), [Jobs & Messaging](jobs-and-messaging.md#jobs--messaging)).
- Choose `ITransactionPort` ownership explicitly: `start()` requires no ambient transaction and resolves after commit; `join()` requires an ambient transaction, creates no savepoint, and resolves before its owner commits. Mismatches throw `SystemException`; neither retries. The primary database proxy participates through ALS, including transactional pg-boss consumers.
- Await shared-transaction writes sequentially and propagate failures. Transaction callbacks are database-only and do not dispatch pipelines. External business effects stay outside the whole transaction; commit-dependent effects/cleanup follow successful `start()`, or use durable follow-up jobs when another caller owns commit. Only refusal audit may bypass the ambient transaction ([Audit](observability.md#audit)).
- Use `TOKEN_DATABASE_CLIENT` for writes, write-decision reads, and cacheable queries; use `TOKEN_DATABASE_REPLICA_CLIENT` only for lag-tolerant presentation reads. A configured replica bypasses ALS; without `DATABASE_REPLICA_URL`, the replica token aliases the primary proxy.
- Post-mutation response queries read the primary without caching; cache eviction alone does not guarantee a fresh response.
- Application-owned row IDs use UUID v7 generated by the owning application/adapter before insert; never use `gen_random_uuid()` for them. Aggregate creation handlers own aggregate IDs; the audit adapter owns audit IDs. Idempotency keys are client-generated UUID v4 request identities.
- Application-owned listings, including audit, use `id DESC`; index the filters/order they rely on.
- Generate Drizzle migrations from schema definitions with `npm run db:generate`; do not handwrite generated migration files.
- Budget connection limits per database endpoint across primary, configured replica, and independent pg-boss pools, multiplied by peak process count including deployment overlap and monitoring processes. Reserve capacity for migrations, administration, and other clients; a proxy does not remove the database connection budget.

## Request Idempotency

- `IIdempotencyPort` owns the outer primary transaction: claim, mutation, success audit, jobs, and minimum replay identity commit or roll back together. Same-key claims settle through PostgreSQL uniqueness under READ COMMITTED; only committed success is retained, rollback leaves the key reusable, and replay skips work.
- `executePrepared()` checks replay before proof/password/external reads. Preparation stays read-only outside the transaction; mutation callbacks are database-only. The final claim settles races even after preparation failure; prepared aggregates retain optimistic-version checks.
- Fingerprints use `IHashingPort.hmacSha256` with storage-specific purpose contexts ([Hashing](security-and-sessions.md#hashing)). Preserve compatibility for deployed fingerprints across context/canonicalization changes. Persist no raw request, credentials, or response blobs; retention and endpoint metadata live in the [idempotency inventory](../docs/idempotency-retry-inventory.md#implemented-request-coordination).

## Adapters

- For read-model queries, filter eligibility in SQL unless rejected state is required for a distinct response or audit. Order applicable predicates as lookup key, soft-delete scope, then eligibility.
- Keep aggregate writers separate from query readers. Writers load/save aggregates through one write port each; readers return read-models. Group readers by source and relevant thin ports, not one adapter per port; composition adapters may combine sources. Use `<module>-reader.adapter.ts` / `<module>-replica-reader.adapter.ts` for primary/replica readers.
- Core adapters follow capabilities (`cache`, `cache-health`, `cache-cleaner`) rather than forced reader/writer pairs.
- `core/redis` owns client factories/classifiers; consuming concerns own connections and failure policies.
- Aggregate rows use integer optimistic versions. `AggregateRoot.version` remains the loaded version (new = 0); writers advance it only in persistence. `save()` inserts at the loaded version or updates to loaded+1 only when the stored version still matches; zero affected rows throw `ResourceConflictException(CONCURRENT_MODIFICATION)`. Do not hold a row-lock transaction across load → save/hashing. Append-only inserts need no version; a single-statement update may omit one only when it is independent of previously read mutable state and enforces all required conditions atomically.
- Creation with replayable identities uses insert-only persistence, never upsert; existence prechecks do not replace unique constraints.
- Writers translate known owned constraint violations to taxonomy exceptions with the original `cause`; database classifiers live in `src/core/database`. Other database errors use `translateConnectionFailure`: known connection failures become `DependencyUnavailableException`, everything else propagates unchanged. Raw health pings/test cleaners are exempt ([Exceptions](exceptions.md#exceptions)).
- Request-path cache adapters absorb only recognized Redis availability failures (`get → null`, `set/delete → no-op`); other errors propagate. Empty keys throw `SystemException`. Durable cache eviction propagates failures for job retry ([CQRS](architecture.md#cqrs), [Jobs & Messaging](jobs-and-messaging.md#jobs--messaging)).
