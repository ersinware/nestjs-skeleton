# Idempotency and Retry-Safety Inventory

## Purpose

This document is the living inventory of production HTTP mutation endpoints and their request-level idempotency / retry-safety characteristics, together with the downstream durable-work safety boundaries that matter to those endpoints.

Update it whenever a mutating production endpoint, its durable jobs, or its retry / redrive behavior changes.

## Boundary: HTTP mutation safety, same-key success replay, and downstream delivery safety

`Current HTTP mutation retry-safe` describes whether repeating the same logical HTTP request can apply the same request-level business mutation more than once.

Endpoints with implemented explicit idempotency require a single UUID v4 `Idempotency-Key` (`400` if missing/invalid). They retain successful operations: same key + same fingerprint replays the original success without repeating mutation, audit, or jobs. Current guards and rate limits still apply. Full responses and credentials are never stored; `204` needs no result identity, redrive retains its original `operationId`.

Explicit same-key success replay preserves the original operation's success semantics, but does not require a byte-identical response payload. A response may be regenerated only when doing so does not repeat the protected mutation or create another unintended side effect. Current authentication, authorization, rate limits, and session revocation/liveness checks remain authoritative.

Protected Redis mutations atomically retain only the request fingerprint, SID, and JTI with the mutation; credentials and full responses are never persisted for replay.

HTTP replay does not guarantee exactly-once queue execution or external effects: consumers can retry, DLQ/redrive can change physical job IDs, and provider retention can expire.

For endpoints that create durable work, HTTP idempotency and downstream consumer delivery safety are classified separately.

## Classification

### Naturally idempotent

Repeating the same logical request leaves the authoritative state equivalent to applying it once.

### Current HTTP mutation retry-safe

Repeating the same logical HTTP request does not apply the same request-level business mutation more than once, even if the retry may currently return a different response.

`Current HTTP mutation retry-safe: Yes` is **not** a downstream exactly-once guarantee.

### Required `Idempotency-Key`

Explicit request-level identity is required when either:

1. repeating the logical request can create another valid request-level mutation, session, rotation, delivery, or operation; or
2. a committed successful mutation can otherwise be reclassified as a later `404`, `409`, `401`, or another conflicting result because the first mutation changed the state that a retry would inspect.

For Redis-backed protected mutations, same key + same fingerprint prevents the protected Redis mutation from running again. Same key + a different fingerprint returns `409`. Current authentication, authorization, rate limits, and session revocation/liveness checks still apply.

A replayed response need not contain byte-identical credentials. Valid credentials may be re-signed from retained live session metadata when that requires no new protected Redis mutation. Tokens and full response bodies are never stored solely for replay.

`Idempotency-Key requirement` records current header support. Unresolved avatar-lifecycle protection remains tracked separately by #30.

HTTP `Idempotency-Key` is distinct from queue `deliveryId`.

## Durable delivery identity and redrive semantics

pg-boss has two different identities:

- **Physical job ID** — one persisted pg-boss job row / attempt.
- **Logical `deliveryId`** — the logical application delivery carried in job data.

For queued email delivery:

```text
provider idempotency key = ${queueName}/${deliveryId}
```

The same logical email retry / redrive keeps the same `deliveryId`, provider key, and semantic payload. A different logical email gets a new `deliveryId`.

Provider idempotency retention is bounded. Delayed retry / redrive may physically send the same logical email again after provider deduplication expires. Email delivery is **at-least-once**, not exactly-once.

## Avatar safety boundary

#30 remains open for the broader upload-proof and stale-cleanup lifecycle.

- replayable upload proofs must not be described as consumed / single-use until #30 implements that guarantee;
- `UserAvatarReplaceConsumer` and `AdminAvatarReplaceConsumer` are not globally retry-safe while the stale `SUPERSEDED` cleanup / reselection race remains open;
- Request replay does not imply global avatar-lifecycle exactly-once behavior.

### Implemented request coordination

Seventeen endpoints implement PostgreSQL-backed request idempotency. Three endpoints implement Redis request coordination: user/admin login (`openSession`) and refresh (`rotateSession`). Five PostgreSQL mutations—user/admin email confirmation, user/admin password change, and user activation completion—return `204 No Content` with no response body, session opening, or credential issuance.

Runtime coverage follows the implemented boundaries:

- [Session adapter unit contracts](../src/core/security/session/adapter/session.adapter.spec.ts): request identity at `KEYS[1]`, HMAC fingerprints, single mutation invocation, refusal mapping, and shared Redis hash tags.
- [Redis session contracts](../test/core/session/session-namespace.e2e-spec.ts): concurrent open/rotate, same-key replay and conflict, refusal without success retention, ambiguous response recovery, independent SID expiry, 300-second request retention, unchanged replay deadlines, repeat-safe logout, and monotonic version updates.
- [Auth HTTP contracts](../test/module/auth/request-idempotency.e2e-spec.ts): required/malformed headers, one-session login replay, refresh replay without reuse remediation, expired-input replay, credential response failure, and logout without a request key.
- [Email/password HTTP contracts](../test/module/email-change/email-change.e2e-spec.ts) and [user activation](../test/module/user/user-activation.e2e-spec.ts): first success and replay return bodyless `204`, with no session opening, token signing, or post-commit account reload; replay also skips aggregate loading and repeated durable effects. Authentication still gates protected retries.
- [PostgreSQL coordination](../test/core/idempotency/idempotency.e2e-spec.ts): concurrent claims, rollback, preparation bypass, and minimal retained metadata.

`IIdempotencyPort` claims a global key on the primary using `INSERT ... ON CONFLICT DO NOTHING` under PostgreSQL's default READ COMMITTED isolation. Concurrent same-key callers wait for settlement: commit permits fingerprint comparison and replay (or `409`), rollback permits a new claim. Claim, mutation, success audit, jobs, and minimum replay identity commit atomically; failures are not retained. Refusal audit remains independently durable.

`executePrepared()` checks retained success before proof/password/current-state preparation; the final claim settles races, including preparation failure.

`idempotency.operation` stores only `key`, HMAC `fingerprint`, `created_at`, and nullable `replay_result_id`. `replay_result_id` retains the redrive operation identifier where needed; the five bodyless mutations use null because their success response has no body. No generic response, raw payload, password, access token, or refresh token is persisted for replay.

Fingerprints use `IHashingPort.hmacSha256(context, canonicalValue)`, with `postgres:idempotency-fingerprint` for PostgreSQL and `redis:idempotency-fingerprint` for Redis; reusable HMAC and shared `HASHING_KEY` validation/rotation: [Hashing](../agent/security-and-sessions.md#hashing). Idempotency owns no separate secret or crypto primitive.

A timeout, connection loss, or lost response after a write leaves the outcome unknown; it does not prove rollback. The server does not automatically retry; clients reuse the same key and semantics. PostgreSQL retention/cleanup is deferred to #3: its rows have no TTL or automatic deletion. Removing a row ends its replay guarantee and allows the key to be claimed again. Redis request success retention is separately bounded to 300 seconds, does not renew on replay, and ends independently of session lifetime.

### Endpoint exceptions and dependencies

Deletion replay skips aggregate loading, audit, jobs, and the immediate Redis version push. `setVersion()` is already monotonic, and the first committed deletion retains durable session reconciliation; no additional Redis request-level protection is required.

- Public activation resend retains missing/ineligible-account `204` no-ops; later account changes cannot turn a same-key retry into a new delivery.
- Logout-all replay confirms the original queued request, not consumer completion.

#### PostgreSQL bodyless success replay

User/admin email confirmation, user/admin password change, and user activation completion recognize PostgreSQL retained success before stale proof/password preparation. Both first success and replay return `204 No Content`; no post-commit account reload, Redis session opening, or token signing occurs. These operations retain null `replay_result_id` and issue no credentials. Authenticated retries still require guard admission; revoked credentials may receive 401 before reaching retained success.

#### Redis login and refresh replay

User/admin login and refresh return `200 OK` with credentials on first success and retained replay. They require explicit request identity and implement their deduplication and mutation in one Lua execution. Request keys are principal-scoped (PostgreSQL keys are global); all keys in each multi-key Lua operation share the same principal hash tag and Redis hash slot. The request marker is `KEYS[1]`; successful replay returns `REPLAYED`, distinct from first `OPENED`/`ROTATED`. Replay preserves SID/JTI and stored deadlines, and re-signs credentials from a live registration without extending session, request, or version retention. Request success retention lasts 300 seconds from the original mutation; expiry ends request deduplication independently of session lifetime. A retry of the original refresh input can replay retained success after that input token expires, while a fresh key cannot rotate an expired input token. Same-key replay does not trigger refresh-token reuse remediation.

Redis session opening, credential signing, and PostgreSQL login audit are not atomic. A failure after opening can leave a retained session without `LOGIN_SUCCESS`; replay skips the audit and does not repair that handoff. This consistency boundary remains #16, separately from request-level mutation deduplication.

#### Naturally repeat-safe Redis operations

Logout, delete-side version mirroring, ban-side version mirroring, and permission-side version mirroring require no additional Redis request identity: `HDEL` is repeat-safe and `setVersion()` advances the Redis version floor monotonically.

## Maintenance Rules

When a mutating production endpoint is added or changed:

1. Update its inventory row from actual controller, handler, persistence, Redis, durable-job, and external-effect behavior.
2. Classify HTTP mutation safety separately from downstream delivery safety.
3. Determine whether a committed success can be recognized before the mutation's own completed state would turn the retry into a different failure.
4. Require `Idempotency-Key` when mutation deduplication is needed, when repeating the request can create another session/rotation/effect, or when committed success semantics would otherwise be lost.
5. Do not add a full response/result blob solely for replay.
6. Do not persist credentials, tokens, raw semantic payloads, or unkeyed secret digests for fingerprint/replay.
7. Do not infer queue exactly-once behavior from HTTP retry safety or same-key success replay.
8. Keep physical pg-boss job identity separate from logical `deliveryId`.
9. Preserve separate ownership for unresolved consistency (#16), avatar lifecycle (#30), and retention/cleanup (#3) boundaries.
10. Revalidate the whole inventory whenever endpoint behavior, durable-job topology, replay semantics, or issue ownership changes.
